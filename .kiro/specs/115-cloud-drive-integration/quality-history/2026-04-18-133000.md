## 🔴 本轮最关键发现（P0 — 方案结构性冲突）

> **结论**：`requirements.md`（Cookie + 网页端 API 方案）与 `design.md` / `tasks.md`（OAuth 2.0 + 开放平台 API 方案）**完全不同一个技术方案**。三文件已严重脱节，Q4（设计覆盖需求）与 Q9（术语一致性）出现大面积崩塌。建议在对这两个 Spec 继续任何增量审核 / 编码前，先决策统一技术方向。

### 方案冲突证据矩阵

| 维度 | requirements.md（Cookie 版本） | design.md / tasks.md（OAuth 版本） | 冲突程度 |
|------|-------------------------------|-----------------------------------|---------|

### 结构性影响量化

- **Q4 设计覆盖**：逐 Cookie 相关需求反查 design.md 组件表：
  - R1（Cookie 会话认证）、R2（Cookie 配置管理）、R3（登录态检测 API）、R26（日志脱敏 Cookie）、R14（回收站 `GET /rb`）、R20（云下载 `/web/lixian/`）、R22（分享 `/share/slist/send/receive`）、R23（多源用户聚合）、R25（12 行错误变体表）在 design.md 中**均无对应组件** → 至少 **9 条需求 0 覆盖**
  - R4-R13a 的网页端字段归一化（`fid→fileId, n→fileName, s→size, fc→category` 等）与 design 中的 `/open/ufile/*` DTO 字段完全不同构 → 近似 **无效覆盖**
- **Q9 术语一致性**：`Cookie_Manager` vs `CloudDriveTokenManager`、`UID/CID/USSID` vs `AppId/AppSecret/AccessToken`、`webapi.115.com` vs `proapi.115.com`、`Signature_Service` vs `ICloudDriveSecretProtector` — 几乎所有核心术语均分裂
- **Q7 任务追溯**：tasks 全部追溯标记指向的"需求编号"按 OAuth 版需求语义理解（如 T2.2 `_需求: 1 (AC3, AC4, AC5, AC6, AC8, AC9)_` 对应 OAuth 令牌生命周期），但当前 requirements R1 是 Cookie 会话，**追溯语义全部悬空或错配**
