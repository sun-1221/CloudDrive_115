# 115 网页端自动化采集器设计文档

## 1. 文档概述

- **文档名称**：115 网页端自动化采集器设计文档
- **文档状态**：评审修订版（2026-04-08）
- **适用对象**：前端开发、自动化工程师、架构设计人员
- **技术栈建议**：`Node.js`、`TypeScript`、`Playwright`、`SQLite`、`NDJSON`

## 2. 项目背景

本项目用于在**用户本人合法登录态**下，对 115 网页端的实际访问行为进行自动化采集，记录页面触发的网络请求与响应信息，并沉淀为可分析、可归档、可导出的接口资产。

传统手工抓包存在以下问题：

- **覆盖不足**：页面多、入口多、状态分支多，手工方式难以稳定覆盖。
- **重复性差**：相同动作在不同时间执行，结果很难严格一致。
- **整理成本高**：抓到的 HAR、截图、零散请求难以快速形成接口文档。
- **难以支撑重写**：仅有零散 URL 不足以支持页面级重构，需要页面、动作、接口三者的映射关系。

因此，需要构建一套自动化采集器，将浏览器驱动、网络监听、原始数据落盘、接口归一化与报表导出串联成完整流程。

## 3. 设计目标

### 3.1 核心目标

- **自动化采集**：自动执行网页端场景并监听网络请求。
- **高覆盖记录**：按页面、动作、接口三个维度记录请求和响应。
- **结构化输出**：输出 `JSON`、`CSV`、`Markdown`、`OpenAPI` 草稿等结果。
- **支持前端重写**：为后续页面重写、接口适配层和调用映射提供依据。
- **支持重复运行**：基于已保存登录态稳定重复执行采集任务。

### 3.2 非目标

- **不绕过鉴权**：不负责破解登录、签名、风控或设备校验。
- **不承诺穷尽所有隐藏接口**：仅采集网页端实际触发且可观测的接口。
- **不做通用爬虫平台**：当前聚焦目标站点和目标功能。
- **不承担完整 API 生命周期管理**：输出接口资产，但不替代专业 API 平台。

## 4. 适用范围与边界

### 4.1 适用范围

- **网页端自动化采集**：采集 `XHR`、`fetch`、部分 `WebSocket` 连接与消息摘要。
- **合法登录态采集**：通过用户本人已授权会话执行。
- **接口归档与分析**：输出接口清单、页面到接口映射、场景覆盖报告。

### 4.2 边界说明

- **仅采集目标域名流量**：避免无关第三方请求污染结果。
- **仅采集网页端可观测行为**：不保证覆盖未触发、隐藏或灰度接口。
- **默认脱敏导出**：Cookie、Token、用户标识等敏感信息不进入公开报表。

## 5. 总体方案

系统按照“执行、采集、解析、存储、导出”五个阶段组织：

```text
CLI
-> 加载配置
-> 启动浏览器并恢复登录态
-> 调度场景执行
-> 监听并记录网络请求/响应
-> 原始记录落盘
-> （可选）归一化与接口聚合
-> （可选）输出接口台账和报告
```

> 注：归一化与导出默认不随 `collect` 自动执行，需通过 `--analyze` 参数或独立运行 `analyze` / `export` 命令触发。

### 5.1 总体原则

- **以场景覆盖为核心**：不是单纯收集 URL，而是按业务行为组织采集。
- **原始数据可重放**：保留原始记录，后续可重新归一化分析。
- **采集与分析解耦**：采集器负责记录，解析器负责归档与聚合。
- **模块职责单一**：浏览器、场景、采集、解析、存储、导出分层清晰。

### 5.2 运行时隔离与执行模型

- **一次 `collect` 对应一次 `run`**：每次执行都会生成唯一 `runId`，作为本轮采集、分析和导出的统一边界。
- **场景默认串行执行**：首版默认不并发执行顶层场景，优先保证稳定性、可追溯性和对目标站点的低扰动。
- **场景级上下文隔离**：每个场景默认创建独立 `BrowserContext` 与独立 `Page`，共享同一份基线登录态，但不共享运行期间产生的状态副作用。
- **失败隔离**：单个场景的普通失败（选择器失效、超时、业务异常等）不会中断整轮采集；失败场景会独立记录错误、截图、trace 和退出原因。但鉴权失败属于 run 级致命错误，不适用场景级失败隔离，应中止后续场景执行（详见 9.1）。
- **子页面归属**：若场景执行过程中出现弹窗页、预览页或新标签页，则它们归属于当前场景，并作为该场景的子页面记录。
- **产物隔离**：每个 `run` 和每个场景都拥有独立 artifact 目录，避免不同批次和不同场景之间的数据互相污染。
- **共享模式不纳入 MVP**：多场景共享同一运行时上下文的模式不纳入首版，避免引入难以定位的状态污染问题。

## 7. 模块设计

### 7.1 CLI 层

CLI 负责对外暴露命令入口。

建议命令：

- **`login`**：打开浏览器，人工完成登录并保存 `storageState`。
- **`collect`**：执行一个或多个场景，采集网络请求并落盘原始记录。默认只产出原始数据，不自动触发归一化；可通过 `--analyze` 参数在采集结束后自动进入分析流程。
- **`replay`**：基于已有登录态重新执行指定场景的采集流程，产生新的 `runId`。与 `collect` 的区别在于 `replay` 会复用上一次 `run` 的场景配置和参数，便于对比不同时间或状态下的采集结果。
- **`analyze`**：独立的后处理命令，对已有原始记录做归一化、接口聚合、去重和统计。接收一个或多个 `runId` 作为输入，分析结果写入对应 `run` 目录的 `normalized/` 和 `reports/` 下。可反复运行，用于升级归一化算法后重新分析历史数据。
- **`export`**：导出 `JSON`、`CSV`、`Markdown`、`OpenAPI` 草稿。

### 7.2 应用调度层

`app` 层用于组织整个生命周期。

核心职责：

- **加载配置**
- **初始化浏览器上下文**
- **注册监听器**
- **执行场景**
- **管理任务生命周期**
- **汇总结果并触发导出**

### 7.3 浏览器管理层

`browser` 层负责 Playwright 浏览器实例、上下文和页面管理。

核心职责：

- **浏览器启动与销毁**
- **上下文创建与复用**
- **会话状态读写**
- **页面统一配置**
- **超时、UA、viewport 等运行参数控制**

核心模块：

- **`browser-manager`**：浏览器生命周期管理
- **`context-manager`**：上下文创建、登录态恢复
- **`page-manager`**：页面创建、页面级事件接入
- **`session-store`**：读写 `storage-state.json`

### 7.4 场景层

`scenario` 层负责定义采集流程。

设计原则：

- **一个场景只描述一种业务流程**
- **场景按功能而非页面碎片拆分**
- **场景之间可独立运行**
- **场景可配置前置条件与标签**

推荐首批场景：

- **`home`**：首页初始化接口采集
- **`files`**：文件列表、分页、切换目录
- **`search`**：搜索请求、有结果/无结果分支
- **`share`**：分享相关接口
- **`preview`**：图片、视频、文档预览相关接口

### 7.5 动作层

`actions` 层封装页面通用操作。

典型动作：

- **页面跳转**
- **点击菜单和按钮**
- **输入表单**
- **等待列表加载完成**
- **判断弹窗是否出现**
- **读取 DOM 状态**

动作层的作用：

- **复用 UI 操作能力**
- **降低场景脚本复杂度**
- **集中处理选择器变动**
- **集中实现重试和错误记录**

### 7.6 采集层

`capture` 层是整个系统的核心。

主要职责：

- **监听 request/response**
- **关联请求开始与响应完成事件**
- **记录请求体与响应体**
- **记录状态码、耗时、内容类型**
- **记录页面 URL 与当前动作上下文**
- **按需输出 HAR**
- **记录 WebSocket 建立与消息摘要**

采集记录应具备可追溯性，能够回答以下问题：

- **这个请求由哪个场景触发**
- **这个请求由哪个页面动作触发**
- **这个请求在什么时间发生**
- **它的请求参数和返回结构是什么**

### 7.6.1 内容采集策略

- **文本内容优先保留**：对 `JSON`、`HTML`、`plain text` 等可解析文本响应优先记录完整内容；当超过 `maxBodySize` 时仅保留截断内容、长度和哈希。
- **二进制内容只保留摘要**：对图片、音视频、下载流和其他二进制内容默认不保存完整 body，仅记录 `contentType`、大小、哈希和来源 URL。
- **请求体与响应体均可配置**：是否保存 body、保存上限和是否对特定域名或路径例外处理，统一由配置驱动。
- **预检请求单独标识**：`OPTIONS` 预检请求默认保留在原始记录中，但在接口台账导出阶段默认忽略。

### 7.6.2 异常与特殊请求处理

- **失败请求必须可诊断**：请求失败时必须记录失败阶段、失败原因、超时信息和是否被浏览器主动中止。
- **重定向链必须保留**：对 3xx 跳转请求保留 `redirectChain`，便于分析真实入口与最终资源地址。
- **缓存命中需要显式标记**：缓存返回、304 或无法读取完整 body 的场景要保留标记，避免误判为空响应。
- **WebSocket 仅做轻量采集**：MVP 仅记录握手信息、连接生命周期和消息摘要，不做完整协议级重放。

### 7.7 解析层

`parser` 层负责将原始流量转成接口资产。

核心能力：

- **URL 归一化**：去掉时间戳、随机串和无意义动态参数
- **请求体归一化**：保留结构，屏蔽易变值
- **接口指纹生成**：根据多级签名体系聚合接口（详见 7.7.2）
- **响应结构推断**：抽取字段结构、分页结构、错误码特征
- **样本合并**：合并相同接口在不同场景下的调用样本

### 7.7.1 归一化规则

- **Query 参数分层处理**：时间戳、随机数、追踪 ID 等噪声字段默认忽略；分页、排序、目录 ID、业务类型等语义字段默认保留。
- **Body 保留结构与关键语义字段**：归一化时保留对象结构、字段类型和关键动作字段，如 `action`、`op`、`type`、`method`。
- **Header 不直接参与语义归并**：动态鉴权值不参与接口聚合，但要保留鉴权方式识别结果，如 Cookie、Bearer、自定义签名头。
- **路径参数尽量抽象**：对明显的资源 ID、分享码、文件 ID 等路径片段做参数化归一，减少因实例值不同造成的重复接口。

### 7.7.2 接口指纹与冲突降级

- **传输签名**：`method + pathname`，用于粗粒度聚类。
- **请求签名**：`method + normalizedPath + queryShape + bodyShape`，用于大部分接口去重。
- **语义签名**：当请求中存在 `action/type/op/method` 等关键字段时，将其并入签名，避免网关式接口被误合并。
- **冲突优先拆分**：当同一路径出现明显不同响应结构、错误码集合或关键语义字段差异时，优先拆成多个接口模型而不是强行归并。
- **低置信度输出**：无法确定是否应合并的接口，输出为低置信度记录并进入人工复核列表。

### 7.8 存储层

`storage` 层负责数据落盘与索引。

建议采用双轨存储：

- **原始数据**：使用 `NDJSON` 逐条写入，作为事实真相源，适合高频追加和后续重放
- **索引数据**：使用 `SQLite`，作为派生分析索引，适合做查询、统计和去重分析

目录划分建议：

- **`output/runs/<runId>/raw`**：按场景保存原始请求流，便于局部重放与局部分析。
- **`output/runs/<runId>/normalized`**：归一化后的接口模型与中间结果
- **`output/runs/<runId>/reports`**：报表、接口台账与导出文档
- **`output/runs/<runId>/har`**：HAR 文件
- **`output/runs/<runId>/screenshots`**：错误截图
- **`output/runs/<runId>/traces`**：Playwright trace

### 7.8.1 存储约束

- **原始记录只追加不就地改写**：原始 `NDJSON` 为真相源，后续清洗、归一化和脱敏通过派生文件完成。
- **分析索引可重建**：`SQLite` 与所有导出结果都必须能够从原始记录重新构建。
- **清理以 `run` 为粒度**：`clean-output` 按 `runId` 目录清理，避免误删仍需复盘的单个场景产物。

### 7.9 导出层

`exporter` 层负责生成项目交付物。

建议支持：

- **`JSON`**：供程序继续处理
- **`CSV`**：供人工筛选和接口归档
- **`Markdown`**：供文档沉淀
- **`OpenAPI` 草稿**：供前端适配层、Mock 或二次开发使用

### 7.10 安全层

`security` 层用于控制边界与脱敏。

职责包括：

- **限制采集域名范围**
- **过滤无关第三方请求**
- **脱敏 Cookie、Token、用户 ID 等敏感字段**
- **防止敏感值进入导出报表**
- **控制原始数据仅本地保留，不进入版本库**

## 8. 数据模型设计

### 8.1 CollectorConfig

用于描述运行时配置。

建议字段：

- **`baseUrl`**：入口 URL
- **`allowedDomains`**：允许采集的域名白名单
- **`headless`**：是否无头运行
- **`storageStatePath`**：登录态保存路径
- **`outputDir`**：输出目录
- **`scenarioIds`**：执行的场景列表
- **`captureResponseBody`**：是否记录响应体
- **`maxBodySize`**：单条 body 记录大小上限
- **`timeoutMs`**：页面与动作超时
- **`scenarioIntervalMs`**：场景之间的等待间隔
- **`actionDelayMs`**：动作之间的基础延迟
- **`pageStabilityMs`**：页面加载稳定等待时间
- **`maxRetries`**：单步最大重试次数
- **`retryBackoffMs`**：重试退避基数

### 8.2 ScenarioContext

场景运行时上下文。

建议字段：

- **`runId`**
- **`scenarioId`**
- **`page`**
- **`browserContext`**
- **`config`**

## 9. 执行流程设计

### 9.1 登录态准备

- **首次执行**：通过 `login` 命令打开浏览器，人工完成登录。
- **状态保存**：将登录态写入 `storageState` 文件。
- **后续执行**：自动加载已有登录态，减少重复登录。
- **启动时校验**：`collect` 启动后、执行场景前，先发起一次轻量级登录态检查（如请求用户信息接口）；若失败则中止采集并提示重新执行 `login`。
- **运行中过期处理**：若场景执行过程中检测到鉴权失败响应（如 401、特定业务错误码），将当前场景标记为 `failed`，后续场景暂停执行，并在 `manifest.json` 中记录 `sessionExpired` 状态。

### 9.2 采集流程

1. **加载配置与场景列表，并生成 `runId`**
2. **初始化 `manifest.json` 与配置快照**
3. **启动浏览器并恢复基线登录态**
4. **逐个场景创建独立 `BrowserContext` 与 `Page`**
5. **为当前场景注册 request/response 监听器并执行动作序列**
6. **按 `runId/scenarioId` 维度写入原始记录和调试产物**
7. **关闭场景上下文并继续下一个场景**
8. **写入 `manifest.json` 并关闭浏览器**
9. **若指定了 `--analyze`，则自动进入归一化、接口聚合和报表导出流程；否则仅落盘原始数据**

### 9.3 失败处理

- **场景失败**：记录错误、截图、trace，并继续下一个场景。
- **单步失败**：支持有限次重试，避免偶发页面抖动影响结果。
- **选择器失效**：记录 DOM 探测信息，便于后续调整动作层。
- **网络超时**：标记超时状态，同时保留已成功采集的结果。

### 9.4 运行约束与速率限制

- **默认串行执行**：MVP 不并发执行顶层场景，避免对目标站点造成不必要压力。
- **动作节奏可配置**：场景间隔、关键动作等待时间和页面稳定等待策略均由配置控制。
- **重试必须有上限**：单步重试次数受限，并采用退避策略，避免故障时无限重放。
- **禁止激进式探测**：不通过爆破式路径遍历、超高频刷新或异常参数探测来追求覆盖率。

## 10. 场景设计原则

### 10.1 拆分原则

- **按业务流程拆分，不按页面碎片拆分**
- **场景之间应尽量无强依赖**
- **每个场景应具备明确前置条件**
- **场景输出应能映射到页面和接口维度**

### 10.2 推荐初始场景

- **首页初始化**：采集用户信息、初始化配置、首页加载接口
- **文件列表**：采集目录切换、分页、排序、列表请求
- **搜索**：采集搜索请求与不同结果状态
- **分享**：采集分享信息读取与相关弹窗请求
- **预览**：采集图片、视频、文档预览相关请求

### 10.3 状态覆盖矩阵

为提高覆盖率，应组合以下状态运行场景：

- **空目录 / 非空目录**
- **单文件类型 / 多文件类型**
- **有搜索结果 / 无搜索结果**
- **有分享记录 / 无分享记录**
- **不同排序方式**
- **普通账号 / 其他权限账号**

### 10.4 场景前置条件与跳过策略

- **场景必须声明前置条件**：包括账号状态、页面入口、所需数据样本和是否依赖已有分享、图片、视频等资源。
- **运行前先做探测**：若关键前置数据不存在，优先尝试在允许范围内动态发现可用样本；仍无法满足时，将场景标记为 `skipped` 并记录原因。
- **优先选择非破坏性路径**：MVP 优先覆盖只读或低副作用流程；涉及写操作的场景需要额外前置开关与审慎确认。
- **场景结果必须可解释**：每个场景最终状态应明确为 `passed`、`failed` 或 `skipped`，不能仅以“未报错”视为成功。

### 10.5 选择器策略

- **优先语义定位**：优先使用 `getByRole`、`getByLabel`、`getByText` 等更稳定的语义定位方式。
- **其次稳定容器定位**：当页面缺少语义锚点时，再使用稳定区域容器结合文本或属性做组合定位。
- **避免脆弱绝对路径**：场景层不直接写绝对 XPath 或深层级 CSS 选择器，脆弱定位统一收敛到动作层。
- **选择器故障可诊断**：定位失败时要输出 DOM 探测结果、候选元素信息和当前页面截图，便于后续修复。

### 11.4 Run 目录规范

## 12. 安全与合规设计

### 12.1 基本原则

- **仅在合法授权会话内运行**
- **不绕过鉴权、风控或访问控制**
- **不伪造非必要身份信息**
- **不采集无关域名**
- **默认对外导出脱敏版本**

### 12.2 脱敏策略

默认脱敏以下内容：

- **`Cookie`**
- **`Authorization`**
- **`token`**
- **用户 ID**
- **手机号**
- **邮箱**
- **分享码**
- **设备标识**

### 12.3 版本库策略

- **`state/auth`** 加入 `.gitignore`
- **`output/runs`** 加入 `.gitignore`
- **报表导出默认使用脱敏值**
- **敏感配置使用 `.env` 管理**

### 12.4 操作性安全规则

- **白名单优先**：采集范围默认由域名白名单控制，黑名单仅作为补充规则。
- **原始数据默认仅本地保留**：原始 body、鉴权头和登录态文件不作为共享产物导出。
- **日志默认不打印敏感值**：运行日志中默认不输出完整 Cookie、Authorization 和完整请求体，只输出摘要或脱敏片段。
- **脱敏发生在导出阶段**：原始真相源保持原样本地保存，面向共享和版本管理的派生产物必须统一脱敏。
- **共享设备建议使用系统级保护**：若运行环境为共享机器，建议对 `state` 与 `output/runs` 使用操作系统级目录加密或权限隔离。

## 14. MVP 设计

### 14.1 MVP 范围

首版只做最小闭环：

- **人工登录并保存会话**
- **执行 3 个核心场景**
  - 首页
  - 文件列表
  - 搜索
- **采集 `XHR` 与 `fetch`**
- **保存原始请求与响应**
- **使用传输签名（`method + normalizedPath`）去重**（即三级签名体系的第一级，详见 7.7.2；请求签名与语义签名在第二阶段实施）
- **导出 `JSON` 与 `CSV`**

### 14.2 暂不纳入 MVP

- **完整 WebSocket 深度解析**
- **复杂弹窗与右键菜单全自动遍历**
- **多账号差异分析**
- **高质量 OpenAPI 自动生成**
- **复杂路由自动发现**

## 15. 风险与应对

### 15.1 页面结构变动

- **风险**：元素定位失效，导致场景中断。
- **应对**：动作层集中封装选择器，避免在场景中散落定位逻辑。

### 15.2 覆盖率不足

- **风险**：自动化难以触发某些边缘路径。
- **应对**：采用“主流程自动化 + 状态矩阵补采 + 人工补盲”策略。

### 15.3 数据量膨胀

- **风险**：响应体、HAR、截图过大。
- **应对**：限制 body 记录大小，对二进制只保留摘要。

### 15.4 敏感信息泄露

- **风险**：原始采集结果可能包含登录态和个人信息。
- **应对**：原始文件仅本地保留，对外报告统一脱敏。

### 15.5 接口聚合误判

- **风险**：不同接口被错误合并，或相同接口被重复拆分。
- **应对**：结合路径、方法、请求结构和场景标签进行多维聚合。

## 16. 实施计划

### 16.1 第一阶段：采集闭环

目标：

- **打通登录、采集、原始落盘闭环**

交付：

- **`login` 命令**
- **`collect` 命令**
- **原始采集日志**

完成判定：

- **能够稳定生成 `storageState` 并复用登录态**
- **每次采集都能生成带 `runId` 的 `manifest.json`**
- **至少一个场景能够输出结构完整的原始 `NDJSON` 记录**

### 16.2 第二阶段：接口归档

目标：

- **完成归一化、聚合、接口去重**

交付：

- **`analyze` 命令**

- **基础统计报告**

完成判定：

- **能够从原始记录重建 `SQLite` 索引**
- **能够输出去重后的接口清单与低置信度复核列表**
- **能够按场景统计接口样本数与状态码分布**

### 16.3 第三阶段：重构支撑

目标：

- **形成页面到接口映射与设计文档**

交付：

- **Markdown 报告**
- **OpenAPI 草稿**
- **场景覆盖报告**

完成判定：

- **能够将场景、动作与接口样本建立映射关系**
- **能够导出可阅读的运行摘要与覆盖报告**
- **能够基于聚合结果生成可用的 OpenAPI 草稿骨架**

## 17. 验收标准

以下标准对应第 16 章三个阶段全部完成后的整体交付验收：

- **能够复用登录态运行**
- **能够稳定执行至少 3 个核心场景**
- **能够记录请求与响应并进行追溯**
- **能够输出去重后的接口清单**
- **能够按场景统计接口来源**
- **能够生成脱敏版本导出结果**

## 18. 结论

本方案的重点并不是一次性“抓到所有 URL”，而是建立一套**可重复、可扩展、可追溯**的网页端接口采集体系。它的最终价值，是为 115 网页端的兼容性重写提供稳定的接口依据、页面调用关系和后续适配层基础。
